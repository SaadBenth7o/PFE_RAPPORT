\chapter{Réalisation de la Solution}

\section*{Introduction}
Ce chapitre présente la réalisation concrète du pipeline de Data Quality sur le Référentiel Tiers de CIH Bank. Tous les contrôles Soda Core s'effectuent exclusivement sur la \textbf{zone RAW} du Data Lake (base Hive \texttt{raw\_nova\_referentieltiers}), qui constitue la copie exacte et non transformée des tables \texttt{CCM\_*} du système opérant Oracle NOVA (\textbf{\uline{le périmètre complet englobe environ 15 tables Tiers ; dans ce chapitre, les tables \texttt{ccm\_npdescription} et \texttt{ccm\_job} serviront d'exemples illustratifs}}). 

Nous détaillerons successivement l'environnement technique de développement et l'accès via MobaXterm, l'implémentation complète du script Soda Core avec Spark, la création des trois tables Hive physiques de persistance, l'intégration dans un DAG Airflow indépendant, la mise en place de la vue virtualisée sous Dremio, et enfin la réalisation du dashboard Tableau.

\subsection{Environnement Hadoop et accès distant}

L'accès aux serveurs du cluster (nœud Edge) et l'exécution des commandes en ligne de commande (CLI) s'effectuent via l'outil \textbf{MobaXterm}. \subsection{Installation hors-ligne de Soda Core}

La politique stricte de sécurité des systèmes d'information (PSSI) de CIH BANK impose une isolation réseau (air-gap) des serveurs du cluster Big Data, interdisant par conséquent tout accès direct à Internet. L'exécution standard de la commande \texttt{pip install} pour rapatrier les dépendances depuis le registre public PyPI est donc impossible.

L'installation de Soda Core et de son connecteur Spark a été réalisée via une procédure d'installation hors-ligne (Offline Wheel Installation) :
\begin{enumerate}
    \item \textbf{Téléchargement des archives (Wheels)} : Sur un poste de travail disposant d'un accès à Internet, les archives des paquets \texttt{soda-core} et \texttt{soda-core-spark} ainsi que l'ensemble de leurs sous-dépendances ont été téléchargées au format \texttt{.whl} dans un dossier dédié via la commande \texttt{pip download}.
    \item \textbf{Transfert sécurisé via MobaXterm} : Le dossier d'archives a été transféré de manière sécurisée en SFTP vers le nœud Edge du cluster grâce à l'interface graphique de MobaXterm.
    \item \textbf{Installation locale} : Sur le nœud Edge, les paquets ont été déployés dans l'environnement virtuel Python (venv) alloué à l'orchestrateur Airflow à l'aide de la commande \texttt{pip}, en forçant la recherche locale :
\end{enumerate}

\begin{lstlisting}[language=bash]
source /opt/airflow/venv_dq/bin/activate
pip install --no-index --find-links=./soda_wheels soda-core-spark
\end{lstlisting}

\section{Implémentation du moteur DQ — Soda Core et Spark}

\subsection{Principe de fonctionnement de Soda Core avec Spark}

Contrairement à d'autres connecteurs SQL classiques (JDBC/ODBC) où Soda Core interroge directement la base de données, la bibliothèque \texttt{soda-core-spark-df} repose sur le traitement en mémoire. Le principe de fonctionnement adopté est le suivant :
\begin{enumerate}
    \item Le script Python crée une \textbf{SparkSession}.
    \item Il charge les tables Hive brutes de la zone RAW (par exemple, \texttt{ccm\_npdescription} et \texttt{ccm\_job}) sous forme de \textbf{DataFrames PySpark}.
    \item Ces DataFrames sont enregistrés en tant que \textbf{vues temporaires} (\texttt{createOrReplaceTempView}).
    \item Soda Core lit le fichier de règles YAML, le traduit automatiquement en \textbf{requêtes Spark SQL}, et exécute ces requêtes directement sur les vues temporaires en utilisant le moteur distribué de Spark.
\end{enumerate}
Cette approche permet d'analyser d'énormes volumes de données de manière distribuée sur le cluster via YARN, sans surcharger le Hive Metastore par de multiples requêtes de contrôle directes.

\subsection{Fichier de configuration YAML (\texttt{checks\_tiers.yml})}

Les règles métier sont définies dans des fichiers YAML de manière déclarative en utilisant le langage SodaCL (Soda Check Language). Ce langage permet de définir non seulement des contrôles simples de validité ou de complétude, mais aussi des contrôles avancés (unicité, fraîcheur, expressions régulières personnalisées).

Conformément aux conventions de nommage, toutes les règles du domaine Tiers (qu'elles concernent les données KYC ou CSP) sont centralisées. À titre d'illustration, nous présentons ci-dessous un extrait enrichi du fichier \texttt{checks\_tiers.yml} regroupant divers contrôles sur les tables \texttt{ccm\_npdescription} et \texttt{ccm\_job} (qui représentent des exemples parmi les 15 tables du périmètre).

\begin{lstlisting}[language=YAML]
# checks_tiers.yml
# Regles Data Quality - Domaine Tiers (KYC & CSP)

checks for ccm_npdescription:
  # --- Completude (Fonction missing_count) ---
  # Verifie qu'aucune ligne ne possede un nom ou prenom nul.
  - missing_count(name) = 0:
      name: "KYC-01 | Completude | Nom"
      attributes:
        criticite: CRITIQUE
        dimension: completeness

  - missing_count(first_name) = 0:
      name: "KYC-02 | Completude | Prenom"
      attributes:
        criticite: CRITIQUE
        dimension: completeness

  # --- Validite (Fonction invalid_count) ---
  # Le genre doit strictement faire partie du referentiel autorise.
  - invalid_count(gender) = 0:
      valid values: ["M", "F"]
      name: "KYC-06 | Validite | Genre hors referentiel"
      attributes:
        criticite: HAUTE
        dimension: validity

  # --- Unicite (Fonction duplicate_count) ---
  # Verifie que l'identifiant radical du client est unique
  - duplicate_count(radical) = 0:
      name: "KYC-07 | Unicite | Doublon sur le radical client"
      attributes:
        criticite: CRITIQUE
        dimension: uniqueness

checks for ccm_job:
  # --- Completude CSP ---
  - missing_count(professional_sector) = 0:
      name: "CSP-01 | Completude | Secteur professionnel"
      attributes:
        criticite: CRITIQUE
        dimension: completeness

  # --- Fraicheur (Fonction freshness) ---
  # S'assure que les donnees chargees datent de moins de 26 heures.
  - freshness(batch_datetime) < 26h:
      name: "CSP-04 | Fraicheur | Retard de mise a jour batch"
      attributes:
        criticite: HAUTE
        dimension: timeliness
        
  # --- Regle SQL personnalisee (Failed Rows) ---
  # Verifie la coherence entre l'employeur et le secteur d'activite.
  - failed rows:
      name: "CSP-05 | Coherence | Employeur non valide pour ce secteur"
      fail query: |
        SELECT radical, employer, professional_sector 
        FROM ccm_job 
        WHERE employer = 'SANS EMPLOI' AND professional_sector != 'CHOMAGE'
      attributes:
        criticite: MOYENNE
        dimension: consistency
\end{lstlisting}

Comme on peut l'observer, SodaCL met à disposition plusieurs fonctions natives :
\begin{itemize}
    \item \texttt{missing\_count} : Calcule le nombre d'enregistrements où la colonne spécifiée est nulle.
    \item \texttt{invalid\_count} : Couplé à l'attribut \texttt{valid values} ou \texttt{valid regex}, il permet de valider le format ou l'appartenance à une liste de référence.
    \item \texttt{duplicate\_count} : Détecte les doublons sur une clé (primaire ou métier).
    \item \texttt{freshness} : Évalue la fraîcheur des données en comparant la date maximale de la colonne avec l'horodatage d'exécution du scan.
    \item \texttt{failed rows} : Permet d'injecter du code SQL pur pour exprimer des règles métiers complexes multi-colonnes ou inter-tables qui ne sont pas couvertes par les fonctions natives.
\end{itemize}

\subsection{Traduction des règles SodaCL en Spark SQL}

En interne, le moteur Soda Core parse ce fichier YAML, identifie la cible de l'environnement (Spark dans notre cas), et traduit dynamiquement chaque condition déclarative en une syntaxe Spark SQL optimisée. Par exemple :
\begin{itemize}
    \item La règle de complétude \texttt{missing\_count(name) = 0} se traduira par une requête d'agrégation mesurant le nombre de valeurs nulles : \newline \texttt{SELECT COUNT(*) FROM ccm\_npdescription WHERE name IS NULL}.
    \item La règle de validité sur le genre (\texttt{invalid\_count(gender) = 0 valid values: ["M", "F"]}) génère un contrôle d'exclusion : \newline \texttt{SELECT COUNT(*) FROM ccm\_npdescription WHERE gender NOT IN ('M','F')}.
    \item Le contrôle de fraîcheur génère un calcul de delta temporel : \newline \texttt{SELECT MAX(batch\_datetime) FROM ccm\_job}. Soda effectue ensuite la soustraction avec \texttt{CURRENT\_TIMESTAMP} au niveau Python.
\end{itemize}
Cette abstraction décharge considérablement le Data Engineer de l'écriture fastidieuse du code SQL répétitif, tout en standardisant la définition de la qualité.

\subsection{Script Python principal (\texttt{dq\_tiers\_checks.py})}

Le script Python principal orchestre l'exécution complète. Après le scan, Soda Core s'exécutant sur Spark ne persiste pas automatiquement les résultats dans Hive (contrairement à l'intégration avec Soda Cloud). C'est le script Python qui doit extraire la matrice de résultats JSON via l'API (méthode \texttt{get\_scan\_results()}), puis aplatir cette structure complexe (dictionnaires imbriqués contenant les métriques, le statut \texttt{pass}/\texttt{fail}, la requête SQL générée, etc.) en tableaux bidimensionnels exploitables.

Conformément à la modélisation statique détaillée dans le chapitre précédent, le script transforme ces extractions en trois DataFrames PySpark distincts, afin de capturer l'ensemble du cycle de vie du contrôle de la qualité, et les persiste dans Hive.

\begin{lstlisting}[language=Python]
# dq_tiers_checks.py
import datetime
from pyspark.sql import SparkSession
from soda.scan import Scan
import json

def run_dq_checks(run_date: str):
    # 1. Initialisation de la SparkSession
    spark = SparkSession.builder \
        .appName("DQ_Tiers_Checks") \
        .enableHiveSupport() \
        .getOrCreate()

    # 2. Chargement des tables physiques Hive en Vues Temporaires Spark
    tables_to_check = ["ccm_npdescription", "ccm_job"]
    for table in tables_to_check:
        df = spark.sql(f"SELECT * FROM raw_nova_referentieltiers.{table}")
        df.createOrReplaceTempView(table)

    # 3. Initialisation du scan Soda Core
    scan = Scan()
    scan.set_data_source_name("spark_df")
    scan.add_spark_session(spark)
    scan.add_sodacl_yaml_file("checks/checks_tiers.yml")

    # 4. Execution distribuee des checks sur le cluster YARN
    scan.execute()
    
    # 5. Extraction des resultats sous forme de dictionnaire Python
    results_dict = scan.get_scan_results()

    # 6. Extraction et structuration en 3 tables physiques
    # (Exemple simplifie de parsing de la matrice JSON)
    history_data = []
    config_data = []
    
    for check in results_dict.get("checks", []):
        run_id = scan._scan_results.get("scanId")
        query_id = check.get("identity")
        
        # Table Historique
        history_data.append((
            run_id, 
            query_id,
            check.get("column", "TRANSVERSE"),
            100.0 if check.get("outcome") == "pass" else 0.0,
            check.get("outcome"),
            check.get("metrics", {}).get("value", 0)
        ))
        
        # Table Configuration
        config_data.append((
            run_id,
            query_id,
            check.get("definition", ""),
            check.get("name"),
            check.get("attributes", {}).get("dimension", ""),
            check.get("attributes", {}).get("criticite", "")
        ))

    # Creation des DataFrames
    df_history = spark.createDataFrame(history_data, 
        ["run_id", "query_id", "colonne_controlee", "score_qualite_pct", 
         "statut", "anomalies_count"])
         
    df_config = spark.createDataFrame(config_data, 
        ["run_id", "query_id", "sql_query", "check_name", 
         "dimension", "criticite"])
         
    # La logique pour le log d'execution (df_exec) suit le meme principe.
    
    # 7. Persistance physique dans Hive (Append Mode)
    df_history.write.mode("append") \
        .saveAsTable("dq_results.consolidated_all_column_history")
    df_config.write.mode("append") \
        .saveAsTable("dq_results.consolidated_all_checks_config")
    # df_exec.write...

    spark.stop()
\end{lstlisting}
Cette implémentation métier sur-mesure nous octroie une maîtrise totale de nos historiques de qualité et respecte strictement la modélisation à trois tables définie lors de la phase de conception.

\section{Création des tables Hive physiques de persistance}

Les trois tables de persistance, définies lors de la conception, sont créées physiquement dans la base Hive \texttt{dq\_results}. Ces tables stockent l'intégralité des métriques : les scores de qualité, les définitions SQL générées, et les statuts d'exécution. L'utilisation du format ORC avec compression Snappy garantit de très hautes performances lors des requêtes analytiques ultérieures.

\begin{lstlisting}[language=SQL]
CREATE DATABASE IF NOT EXISTS dq_results;

-- Table 1 : Historique des scores et resultats
CREATE TABLE dq_results.consolidated_all_column_history (
    run_id STRING, query_id STRING, colonne_controlee STRING, 
    score_qualite_pct DOUBLE, statut STRING, anomalies_count BIGINT
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

-- Table 2 : Configuration des checks (code SQL genere)
CREATE TABLE dq_results.consolidated_all_checks_config (
    run_id STRING, query_id STRING, sql_query STRING, 
    check_name STRING, dimension STRING, criticite STRING
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

-- Table 3 : Journal d'execution (statut technique)
CREATE TABLE dq_results.consolidated_execution_log (
    run_id STRING, query_id STRING, execution_status STRING, 
    error_message STRING, run_timestamp TIMESTAMP
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');
\end{lstlisting}

\section{Création du DAG Airflow indépendant}

Pour garantir un découplage total avec le processus d'ingestion (Sqoop), un nouveau DAG nommé \texttt{daily\allowbreak\_dq\allowbreak\_00} a été configuré dans Airflow. Ce DAG s'exécute quotidiennement à 00h00. Il utilise le \texttt{PythonOperator} couplé à \texttt{subprocess} pour déclencher le job d'évaluation de la qualité. En cas d'échec d'une règle critique, l'orchestrateur remonte une erreur globale.

\begin{lstlisting}[language=Python]
from airflow.operators.python import PythonOperator
import subprocess

def run_dq_tiers(**context):
    run_date = context['ds']
    result = subprocess.run(
        ['python', '/opt/airflow/scripts/dq/dq_tiers_checks.py', '--run_date', run_date],
        capture_output=True, text=True
    )
    if result.returncode != 0:
        raise Exception(f"Echec DQ Tiers:\n{result.stderr}")

    task_id='run_dq_tiers_checks',

\section{Exposition et virtualisation sous Dremio}

Une fois les trois tables physiques alimentées dans Hive (\texttt{consolidated\_all\_column\_history}, \texttt{consolidated\_all\_checks\_config}, et \texttt{consolidated\_execution\_log}), il est nécessaire de consolider ces informations pour les exposer à l'outil BI Tableau de manière claire et optimale. 

Plutôt que de créer une table physique supplémentaire ou d'effectuer des jointures complexes et coûteuses dans Tableau, nous utilisons \textbf{Dremio} en tant que couche de virtualisation sémantique.

Dans Dremio, nous créons un dataset virtuel (VDS) nommé \texttt{fact\allowbreak\_tiers\allowbreak\_dq\allowbreak\_consolidated}. Cette vue réalise dynamiquement la jointure sur les clés uniques \texttt{run\_id} et \texttt{query\_id} des trois tables sources de Hive. Le résultat est une table de faits consolidée, exposant la totalité de la vision 360\textdegree{} des règles DQ, sans aucune duplication physique des données. Dremio accélère les temps de réponse de cette jointure virtuelle grâce à ses réflexions matérielles (Data Reflections).

\section{Réalisation du dashboard Tableau}

\subsection{Connexion Tableau à Dremio et traitement analytique}

Le dashboard Tableau est connecté à Dremio via le connecteur ODBC/JDBC natif. L'unique vue virtuelle \texttt{fact\allowbreak\_tiers\allowbreak\_dq\allowbreak\_consolidated} est importée comme source de données unique dans Tableau Desktop. 

Tous les filtres (par date d'exécution, par sous-domaine, par dimension de qualité), ainsi que toutes les agrégations (comptage de règles, calculs des moyennes de taux de conformité quotidiens ou scores moyens) sont réalisés de manière dynamique au sein des feuilles de calcul (sheets) et des tableaux de bord de Tableau en tirant directement les champs de la table de faits.
