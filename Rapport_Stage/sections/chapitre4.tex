\chapter{Réalisation de la Solution}

\section*{Introduction}
Ce chapitre présente la réalisation concrète du pipeline de Data Quality sur le Référentiel Tiers de CIH Bank. Tous les contrôles Soda Core s'effectuent exclusivement sur la \textbf{zone RAW} du Data Lake (base Hive \texttt{raw\_nova\_referentieltiers}), qui constitue la copie exacte et non transformée des tables \texttt{CCM\_*} du système opérant Oracle NOVA (\textbf{\uline{le périmètre complet englobe environ 15 tables Tiers ; dans ce chapitre, les tables \texttt{ccm\_npdescription} et \texttt{ccm\_job} serviront d'exemples illustratifs}}). 

Nous détaillerons successivement l'environnement technique de développement et l'accès via MobaXterm, l'implémentation complète du script Soda Core avec Spark, la création des trois tables Hive physiques de persistance, l'intégration dans un DAG Airflow indépendant, la mise en place de la vue virtualisée sous Dremio, et enfin la réalisation du dashboard Tableau.

\section{Environnement technique de développement}

\subsection{Environnement Hadoop et accès distant}

Le développement et les tests ont été réalisés dans l'environnement Hadoop sécurisé de CIH Bank. L'accès aux serveurs du cluster (nœud Edge) et l'exécution des commandes en ligne de commande (CLI) s'effectuent via l'outil \textbf{MobaXterm}. MobaXterm est un terminal avancé qui fournit toutes les fonctionnalités réseaux nécessaires (SSH, SFTP) pour se connecter au cluster Big Data. 

Une fois connecté au nœud Edge, l'authentification sécurisée est garantie par le protocole \textbf{Kerberos}. Conformément aux pratiques de l'équipe (identiques à celles utilisées dans les scripts Sqoop), l'accès aux tables Hive et aux fichiers HDFS s'effectue via la commande \texttt{kinit} avec un fichier keytab chiffré associé au compte de service du domaine Tiers.

\subsection{Installation hors-ligne de Soda Core}

La politique stricte de sécurité des systèmes d'information (PSSI) de CIH BANK impose une isolation réseau (air-gap) des serveurs du cluster Big Data, interdisant par conséquent tout accès direct à Internet. L'exécution standard de la commande \texttt{pip install} pour rapatrier les dépendances depuis le registre public PyPI est donc impossible. L'installation de Soda Core et de son connecteur Spark a été réalisée via une procédure d'installation hors-ligne (\textit{Offline Wheel Installation}) articulée en trois étapes :

\paragraph{1. Téléchargement des archives (Wheels) :} Sur un poste de travail disposant d'un accès à Internet, les archives des paquets \texttt{soda-core} et \texttt{soda-core-spark} ainsi que l'ensemble de leurs sous-dépendances ont été téléchargées au format \texttt{.whl} dans un dossier dédié via la commande \texttt{pip download}.

\paragraph{2. Transfert sécurisé via MobaXterm :} Le dossier d'archives a été transféré de manière sécurisée en SFTP vers le nœud Edge du cluster grâce à l'interface graphique de MobaXterm.

\paragraph{3. Installation locale :} Sur le nœud Edge, les paquets ont été déployés dans l'environnement virtuel Python (venv) alloué à l'orchestrateur Airflow à l'aide de la commande \texttt{pip}, en forçant la recherche locale :

\begin{lstlisting}[language=bash]
source /opt/airflow/venv_dq/bin/activate
pip install --no-index --find-links=./soda_wheels soda-core-spark
\end{lstlisting}

\section{Implémentation du moteur DQ — Soda Core et Spark}

\subsection{Arborescence du projet DQ}

Le moteur de Data Quality est structuré en un projet Python autonome, suivant les standards de packaging de l'équipe Data Office (même architecture que les projets \texttt{py-khawarizmi} et \texttt{sddiqi}). Il est packagé via \textbf{PDM} et livré sous forme de fichier \textbf{Wheel} (\texttt{.whl}). L'arborescence suivante présente une vue simplifiée des fichiers essentiels :

\begin{lstlisting}
dq_tiers/                  (Projet DQ - Noeud Edge)
|-- dq_endpoint.py         # Point d'entree (Script principal Python)
|-- configuration/
|   +-- checks_tiers.yml   # Fichier YAML contenant toutes les regles DQ
+-- context/
    |-- scan_runner.py     # Module d'execution des scans Soda Core
    +-- result_writer.py   # Script/Module Python contenant la fonction de persistance
\end{lstlisting}

\subsection{Principe de fonctionnement de Soda Core avec Spark}

Contrairement à d'autres connecteurs SQL classiques (JDBC/ODBC) où Soda Core interroge directement la base de données, la bibliothèque \texttt{soda-core-spark-df} repose sur le traitement en mémoire. Le flux de fonctionnement adopté s'articule de la manière suivante :

\paragraph{Initialisation de la session Spark :} Le script Python crée une \textbf{SparkSession} avec le support du catalogue Hive activé.

\paragraph{Chargement en DataFrames :} Il charge les tables Hive brutes de la zone RAW sous forme de \textbf{DataFrames PySpark}.

\paragraph{Enregistrement des vues temporaires :} Ces DataFrames sont enregistrés en tant que \textbf{vues temporaires Spark} en mémoire via la méthode \texttt{createOrReplaceTempView}.

\paragraph{Traduction et exécution distribuée :} Soda Core lit le catalogue déclaratif de règles YAML, le traduit automatiquement en \textbf{requêtes Spark SQL optimisées}, et soumet ces requêtes distribuées aux exécuteurs du cluster via YARN.

\paragraph{Persistance des métriques et logs :} Les résultats sont extraits sous forme de structures Python, puis formatés et persistés dans les \textbf{3 tables Hive physiques} en mode \texttt{append}.

\subsection{Fichier de configuration YAML (\texttt{checks\_tiers.yml} — exemplaire)}

Les règles métier sont définies de manière déclarative en utilisant le langage \textbf{SodaCL} (Soda Check Language). Ce langage permet de définir des contrôles simples (complétude, validité) ou avancés (fraîcheur, unicité, règles SQL personnalisées). Toutes les règles du domaine Tiers (KYC et CSP) sont regroupées dans un fichier unique, présenté ici en extrait illustratif sur les deux tables d'exemple \texttt{ccm\_npdescription} et \texttt{ccm\_job} :

\begin{lstlisting}[language=YAML]
# checks_tiers.yml
# Regles Data Quality - Domaine Tiers (KYC & CSP)

checks for ccm_npdescription:
  # --- Completude ---
  - missing_count(name) = 0:
      name: "KYC-01 | Completude | Nom"
      attributes:
        criticite: CRITIQUE
        dimension: completeness
        domaine: Tiers

  - missing_count(first_name) = 0:
      name: "KYC-02 | Completude | Prenom"
      attributes:
        criticite: CRITIQUE
        dimension: completeness

  # --- Validite ---
  - invalid_count(gender) = 0:
      valid values: ["M", "F"]
      name: "KYC-06 | Validite | Genre hors referentiel"
      attributes:
        criticite: HAUTE
        dimension: validity
        domaine: Tiers

  # --- Unicite ---
  - duplicate_count(radical) = 0:
      name: "KYC-07 | Unicite | Doublon radical client"
      attributes:
        criticite: CRITIQUE
        dimension: uniqueness

checks for ccm_job:
  # --- Completude CSP ---
  - missing_count(professional_sector) = 0:
      name: "CSP-01 | Completude | Secteur professionnel"
      attributes:
        criticite: CRITIQUE
        dimension: completeness

  # --- Fraicheur ---
  - freshness(batch_datetime) < 26h:
      name: "CSP-04 | Fraicheur | Retard batch superieur a 26h"
      attributes:
        criticite: HAUTE
        dimension: timeliness

  # --- Regle SQL personnalisee (failed rows) ---
  - failed rows:
      name: "CSP-05 | Coherence | Employeur invalide pour ce secteur"
      fail query: |
        SELECT radical, employer, professional_sector 
        FROM ccm_job 
        WHERE employer = 'SANS EMPLOI' AND professional_sector != 'CHOMAGE'
      attributes:
        criticite: MOYENNE
        dimension: consistency
        domaine: Tiers
\end{lstlisting}

Les fonctions d'évaluation SodaCL mobilisées dans notre catalogue de règles s'articulent ainsi :

\paragraph{\texttt{missing\_count} :} Dénombre les enregistrements pour lesquels l'attribut est nul ou vide, permettant de valider l'exhaustivité des champs obligatoires.

\paragraph{\texttt{invalid\_count} :} Évalue la conformité par rapport à un dictionnaire de valeurs autorisées (\texttt{valid values}) ou une expression régulière (\texttt{valid regex}).

\paragraph{\texttt{duplicate\_count} :} Identifie les doublons d'enregistrements sur les clés d'identification métier (telles que le \texttt{radical} client).

\paragraph{\texttt{freshness} :} Mesure l'écart temporel entre la valeur maximale d'une colonne date et l'instant d'évaluation du scan, garantissant l'actualité des données.

\paragraph{\texttt{failed rows} :} Permet d'injecter une requête SQL arbitraire pour vérifier des règles multi-colonnes ou des jointures complexes entre référentiels.

\subsection{Traduction des règles SodaCL en Spark SQL}

En interne, Soda Core identifie la cible (Spark) et traduit chaque règle SodaCL en une requête Spark SQL exécutée sur les vues temporaires. Voici trois exemples de cette traduction :

\medskip
\noindent\textbf{Exemple 1 — Complétude (missing\_count) :}
\begin{lstlisting}[language=YAML]
# >> Regle SodaCL :
- missing_count(name) = 0
\end{lstlisting}
\begin{center}$\Downarrow$ \textit{Traduction automatique par Soda Core}\end{center}
\begin{lstlisting}[language=SQL]
-- >> Requete Spark SQL generee :
SELECT COUNT(*) AS missing_count
FROM ccm_npdescription
WHERE name IS NULL OR TRIM(name) = ''
\end{lstlisting}

\medskip
\noindent\textbf{Exemple 2 — Validité (invalid\_count avec referentiel) :}
\begin{lstlisting}[language=YAML]
# >> Regle SodaCL :
- invalid_count(gender) = 0:
    valid values: ["M", "F"]
\end{lstlisting}
\begin{center}$\Downarrow$ \textit{Traduction automatique par Soda Core}\end{center}
\begin{lstlisting}[language=SQL]
-- >> Requete Spark SQL generee :
SELECT COUNT(*) AS invalid_count
FROM ccm_npdescription
WHERE gender NOT IN ('M', 'F') OR gender IS NULL
\end{lstlisting}

\medskip
\noindent\textbf{Exemple 3 — Fraîcheur (freshness) :}
\begin{lstlisting}[language=YAML]
# >> Regle SodaCL :
- freshness(batch_datetime) < 26h
\end{lstlisting}
\begin{center}$\Downarrow$ \textit{Traduction automatique par Soda Core}\end{center}
\begin{lstlisting}[language=SQL]
-- >> Requete Spark SQL generee (etape 1) :
SELECT MAX(batch_datetime) AS last_batch FROM ccm_job
-- Soda calcule ensuite le delta : CURRENT_TIMESTAMP - last_batch
-- et compare le resultat en heures a la limite de 26h.
\end{lstlisting}

\subsection{Script Python principal (\texttt{dq\_tiers\_checks.py})}

Le script Python principal orchestre l'exécution complète. Soda Core exécutant les checks sur Spark ne persiste pas automatiquement les résultats dans Hive (contrairement à l'intégration cloud). C'est le script Python qui extrait la matrice de résultats JSON via \texttt{get\_scan\_results()}, l'aplatit, puis structure les données en \textbf{3 DataFrames} dont les schémas respectent exactement les tables physiques définies en conception. Les écritures se font systématiquement en mode \textbf{append} pour historiser chaque run journalier.

\begin{lstlisting}[language=Python]
# dq_tiers_checks.py
import datetime, uuid, argparse
from datetime import date
from pyspark.sql import SparkSession, Row
from soda.scan import Scan

def run_dq_checks(run_date: str):
    # --- 1. SparkSession avec support Hive ---
    spark = SparkSession.builder \
        .appName("DQ_Tiers_Checks") \
        .enableHiveSupport() \
        .getOrCreate()

    # --- 2. Chargement des tables RAW en vues temporaires Spark ---
    for table in ["ccm_npdescription", "ccm_job"]:
        spark.sql(f"SELECT * FROM raw_nova_referentieltiers.{table}") \
             .createOrReplaceTempView(table)

    # --- 3. Scan Soda Core ---
    scan = Scan()
    scan.set_data_source_name("spark_df")
    scan.add_spark_session(spark)
    scan.add_sodacl_yaml_file("checks/checks_tiers.yml")
    scan.execute()
    results = scan.get_scan_results()

    run_id = str(uuid.uuid4())
    now = datetime.datetime.now()
    history_rows, config_rows, log_rows = [], [], []

    for check in results.get("checks", []):
        qid      = check.get("identity", str(uuid.uuid4()))
        outcome  = check.get("outcome", "error")
        attrs    = check.get("attributes", {})
        dataset  = check.get("dataset", "")
        col      = check.get("column", "TRANSVERSE")
        score    = 100.0 if outcome=="pass" else (50.0 if outcome=="warn" else 0.0)
        total    = check.get("metrics", {}).get("row_count", 0) or 0
        anomalies= int(check.get("metrics", {}).get("value", 0) or 0)

        # Recuperation SQL genere par Soda Core
        sql_gen = next(
            (q.get("sql","") for q in results.get("queries",[])
             if qid in q.get("name","")), ""
        )
        exec_ok = (outcome != "error")

        # -- Table 1 : consolidated_all_column_history --
        history_rows.append(Row(
            run_id          = run_id,
            query_id        = qid,
            colonne_controlee = col,
            chemin_source   = f"raw_nova_referentieltiers.{dataset}",
            table_dataset   = dataset,
            domaine_metier  = attrs.get("domaine", "Tiers"),
            type_regle_dq   = attrs.get("dimension", "completeness"),
            volume_total    = total,
            lignes_conformes = total - anomalies,
            score_qualite_pct = score,
            statut          = outcome.upper(),
            date_execution  = now,
            criticite       = attrs.get("criticite", "HAUTE")
        ))

        # -- Table 2 : consolidated_all_checks_config --
        config_rows.append(Row(
            run_id    = run_id,
            query_id  = qid,
            run_date  = run_date,
            table     = dataset,
            domain    = attrs.get("domaine", "Tiers"),
            rule      = check.get("name", ""),
            sql       = sql_gen,
            updated_at = now,
            criticite = attrs.get("criticite", "HAUTE")
        ))

        # -- Table 3 : consolidated_execution_log --
        log_rows.append(Row(
            run_id          = run_id,
            query_id        = qid,
            run_date        = run_date,
            table           = dataset,
            domain          = attrs.get("domaine", "Tiers"),
            rule            = check.get("name", ""),
            check_execution_status = "SUCCESS" if exec_ok else "ERROR",
            check_error_message    = "" if exec_ok else str(check.get("error","")),
            check_timestamp        = now,
            run_execution_status   = "SUCCESS",
            run_error_message      = "",
            updated_at             = now
        ))

    # --- 4. APPEND dans les 3 tables Hive physiques ---
    spark.createDataFrame(history_rows).write.mode("append") \
         .saveAsTable("dq_results.consolidated_all_column_history")

    spark.createDataFrame(config_rows).write.mode("append") \
         .saveAsTable("dq_results.consolidated_all_checks_config")

    spark.createDataFrame(log_rows).write.mode("append") \
         .saveAsTable("dq_results.consolidated_execution_log")

    spark.stop()
    print(f"[DQ OK] Run {run_id} | {len(history_rows)} checks persistes.")

if __name__ == "__main__":
    parser = argparse.ArgumentParser()
    parser.add_argument("--run_date", default=str(date.today()))
    args = parser.parse_args()
    run_dq_checks(args.run_date)
\end{lstlisting}

Le mode \texttt{append} est fondamental : à chaque exécution nocturne du DAG \texttt{daily\_dq\_00}, une nouvelle tranche de résultats est ajoutée aux trois tables sans écraser les données historiques. Cette accumulation constitue la base temporelle qui alimente les tendances et analyses dans le dashboard Tableau.

\section{Création des tables Hive physiques de persistance}

Les trois tables de persistance, définies lors de la conception, sont créées physiquement dans la base Hive \texttt{dq\_results}. Ces tables stockent l'intégralité des métriques : les scores de qualité, les définitions SQL générées, et les statuts d'exécution. L'utilisation du format ORC avec compression Snappy garantit de très hautes performances lors des requêtes analytiques ultérieures.

\begin{lstlisting}[language=SQL]
CREATE DATABASE IF NOT EXISTS dq_results;

-- Table 1 : Historique des scores et resultats
CREATE TABLE dq_results.consolidated_all_column_history (
    run_id STRING, query_id STRING, colonne_controlee STRING, 
    score_qualite_pct DOUBLE, statut STRING, anomalies_count BIGINT
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

-- Table 2 : Configuration des checks (code SQL genere)
CREATE TABLE dq_results.consolidated_all_checks_config (
    run_id STRING, query_id STRING, sql_query STRING, 
    check_name STRING, dimension STRING, criticite STRING
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');

-- Table 3 : Journal d'execution (statut technique)
CREATE TABLE dq_results.consolidated_execution_log (
    run_id STRING, query_id STRING, execution_status STRING, 
    error_message STRING, run_timestamp TIMESTAMP
) STORED AS ORC TBLPROPERTIES ('orc.compress'='SNAPPY');
\end{lstlisting}

\section{Création du DAG Airflow indépendant}

Pour garantir un découplage tout en sécurisant la chaîne de traitement, un nouveau DAG nommé \texttt{daily\allowbreak\_dq\allowbreak\_00} a été configuré dans Airflow. Ce DAG s'exécute quotidiennement à 00h00 et implémente le pattern de \textbf{Data Quality Gate (Circuit Breaker)}. 

La première tâche exécute exclusivement les contrôles de pipeline (fraîcheur, volumétrie). Si l'ingestion a échoué en amont, cette tâche remonte une alerte critique et stoppe immédiatement l'exécution. Ce n'est que si le pipeline est validé que la seconde tâche s'exécute pour calculer les scores métier de qualité (validité, complétude, etc.), évitant ainsi de générer de faux rapports sur des données périmées.

\begin{lstlisting}[language=Python]
from airflow.operators.python import PythonOperator
import subprocess

def run_pipeline_checks(**context):
    result = subprocess.run(
        ['python', '/opt/airflow/scripts/dq/dq_pipeline_checks.py', '--run_date', context['ds']],
        capture_output=True, text=True
    )
    if result.returncode != 0:
        raise Exception(f"Alerte Pipeline (Circuit Breaker declenche):\n{result.stderr}")

def run_business_checks(**context):
    result = subprocess.run(
        ['python', '/opt/airflow/scripts/dq/dq_business_checks.py', '--run_date', context['ds']],
        capture_output=True, text=True
    )
    if result.returncode != 0:
        raise Exception(f"Echec DQ Tiers:\n{result.stderr}")

pipeline_task = PythonOperator(
    task_id='run_pipeline_checks',
    python_callable=run_pipeline_checks,
    dag=dag
)

business_task = PythonOperator(
    task_id='run_business_checks',
    python_callable=run_business_checks,
    dag=dag
)

# Dependance : Les regles metier ne s'executent que si l'ingestion est saine
pipeline_task >> business_task
\end{lstlisting}

\section{Exposition et virtualisation sous Dremio}

Une fois les trois tables physiques alimentées dans Hive (\texttt{consolidated\_all\_column\_history}, \texttt{consolidated\_all\_checks\_config}, et \texttt{consolidated\_execution\_log}), il est nécessaire de consolider ces informations pour les exposer à l'outil BI Tableau de manière claire et optimale. 

Plutôt que de créer une table physique supplémentaire ou d'effectuer des jointures complexes et coûteuses dans Tableau, nous utilisons \textbf{Dremio} en tant que couche de virtualisation sémantique.

Dans Dremio, nous créons un dataset virtuel (VDS) nommé \texttt{fact\allowbreak\_tiers\allowbreak\_dq\allowbreak\_consolidated}. Cette vue réalise dynamiquement la jointure sur les clés uniques \texttt{run\_id} et \texttt{query\_id} des trois tables sources de Hive. Le résultat est une table de faits consolidée, exposant la totalité de la vision 360\textdegree{} des règles DQ, sans aucune duplication physique des données. Dremio accélère les temps de réponse de cette jointure virtuelle grâce à ses réflexions matérielles (Data Reflections).
